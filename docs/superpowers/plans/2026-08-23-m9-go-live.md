# M9 — Go Live: signed webhooks, guarded metrics, real-PR validation

**Status: complete** (2026-08-23), except hosting, which is deliberately deferred.

## Context

Everything from M1 through M8 — real diff fetch, LLM enrichment, idempotent comment upsert,
Redis durability, semantic corpus, check runs with line-mapped annotations, and M8's event
filter and skipped-review path — had only ever run against fakes and `curl`. 504 tests passed,
but **no part of the pipeline had touched real GitHub data**.

M9 closed that. Three things had to happen in order: harden the endpoint for exposure, point
it at a real GitHub App, and prove the pipeline against actual pull requests.

**Outcome achieved:** Sentinel reviews real PRs on `notjwp/test-repo` — fetching the diff,
running all four engines, enriching findings through the LLM, upserting one comment, and
posting a check run whose annotations land on the correct file lines.

### Decisions taken

- **Signature verification:** fail-closed **in production only**, via a new `ENVIRONMENT`
  setting. Dev and the test suite are untouched.
- **Queue:** Redis, via the `redis:7-alpine` service already in `docker-compose.yml`.
- **Hosting: deferred.** No always-on host was provisioned. Validation does not require one,
  and every free option needs a CLI install (`flyctl`) or a VPS. Sentinel currently runs
  locally and is triggered on demand — a legitimate end state, see Phase 5.
- **No tunnel.** The original plan used a Cloudflare Tunnel to receive real deliveries. It
  was dropped: `cloudflared` is an install, and the behaviors it would have proven were
  covered instead by replaying GitHub-shaped signed deliveries at the local endpoint
  (Phase 4b). What a tunnel uniquely proves is the *network path*, which is a property of
  DNS/TLS, not of this codebase.

## Phase 1 — code changes before exposure ✅

### 1.1 `ENVIRONMENT` + fail-closed startup

`sentinel/config/settings.py` gained `ENVIRONMENT` (default `"development"`).
`main.verify_startup_config()` raises when `ENVIRONMENT=production` and `ENABLE_GITHUB` is on
without `GITHUB_WEBHOOK_SECRET` — a misconfigured deploy fails loudly instead of serving an
unsigned endpoint.

It is a pure, importable function called **before** the worker task is created; raising after
that point would orphan the task.

### 1.2 `/metrics` bearer gate

`METRICS_TOKEN` guards `GET /metrics` via a route dependency in
`sentinel/api/metrics_controller.py`, mirroring `webhook_security.verify_webhook_signature`.
Compared as **bytes** so a malformed header returns 401 rather than raising 500 — the same
lesson as the M0 HMAC fix. Unset leaves the endpoint open (the dev default).

### 1.3 `${PORT:-8000}`

`Dockerfile` CMD and HEALTHCHECK honor `$PORT`, so a host that injects one is a config change
rather than a code change.

**Verified in a real container:** production-without-secret refuses to boot; with a secret,
`PORT=9000` serves `/health`; `/metrics` 401→200; unsigned webhook 401; correctly signed
`pull_request/opened` → `{"status":"queued"}`; signed `ping` → `{"status":"ignored","event":"ping"}`.

## Phase 2 — running the service (no tunnel, no installs) ✅

### 2.1 Secrets

```bash
python -c "import secrets; print(secrets.token_hex(32))"   # x2
```

`.env` (git-ignored) carries `GITHUB_WEBHOOK_SECRET`, `METRICS_TOKEN`, and
`ENVIRONMENT=production`. Setting production locally is deliberate: it exercises 1.1 on the
machine you develop on.

> **Gotcha this created.** `settings.py` calls `load_dotenv()` at import, so the new secret
> leaked into the test suite and 46 webhook tests began returning 401 against unsigned
> requests. CI never saw it (no `.env` on the runner) — it failed only on the machine closest
> to shipping. Fixed by `sentinel/tests/conftest.py`, an autouse fixture that clears
> `GITHUB_WEBHOOK_SECRET`, `METRICS_TOKEN`, and `ENVIRONMENT` per test. **Keep the suite
> hermetic**: any future setting that changes how requests are *gated* belongs in that list.

### 2.2 Start

```bash
docker compose up --build -d
docker compose logs -f sentinel
curl -s localhost:8000/health
```

If the container exits instead of starting, that is 1.1 working — the secret is missing.

### 2.3 Triggering a review

Sentinel only makes **outbound** calls to do a review: the worker fetches the PR from the
GitHub API itself. No inbound reachability is needed to exercise the pipeline. With a secret
configured, the trigger must be signed:

```bash
BODY='{"repo":"notjwp/test-repo","pr_number":2}'
SECRET=$(grep GITHUB_WEBHOOK_SECRET .env | cut -d= -f2)
SIG=$(python -c "import hmac,hashlib,sys;print('sha256='+hmac.new(sys.argv[2].encode(),sys.argv[1].encode(),hashlib.sha256).hexdigest())" "$BODY" "$SECRET")
curl -s -X POST localhost:8000/webhook -H 'Content-Type: application/json' \
  -H "X-Hub-Signature-256: $SIG" -d "$BODY"
```

No `X-GitHub-Event` header, so the M8 filter passes it through (the filter only applies when
the header is present).

## Phase 3 — GitHub App ✅

Installed on **`notjwp/test-repo`**. Permissions: Pull requests R/W, Issues R/W, **Checks
R/W**, Contents Read-only.

**The Checks permission was already granted** — `create_check_run` returned True on the first
attempt and no installation approval was pending. This had been flagged as the most likely
failure mode; it was a non-issue here. It remains the first thing to check if a future
install shows "comment posted, no check run" (`check run=False` in the log).

Webhook configuration on the App was **not** performed — no public URL. See Phase 5.

## Phase 4 — live validation against real PRs ✅

Against `notjwp/test-repo`, using the signed local trigger.

| # | Check | Result |
|---|---|---|
| 1 | App auth: JWT → installation token | ✅ first real run |
| 2 | Fetch → assess → comment → check run (PR #1) | ✅ Risk HIGH |
| 3 | **Annotation line accuracy, mid-file** (PR #2) | ✅ **`billing.py:12`, `:13`** |
| 4 | Idempotent upsert | ✅ 4 posts → 1 comment |
| 5 | Docs-only PR (PR #3) | ✅ `success` + 2 doc annotations |
| 6 | Crash recovery | ✅ `Recovered 1 orphaned job(s)` |
| 7 | Fail-closed boot / `/metrics` 401→200 / unsigned 401 | ✅ |
| 8 | LLM enrichment | ✅ real explanations and fixes |

**On check 3 — the one that mattered.** PR #1 replaced a whole file (`@@ -1 +1,4 @@`), so
code-line N mapped to line N and a naive implementation would have passed. PR #2 was built
specifically to discriminate: secrets inserted mid-file inside `apply_discount`, at lines
12–13 of a 25-line file. Annotations landed on 12 and 13. **The M6 `line_map` hunk arithmetic
is correct against real patches.** Any future change to `_added_lines_with_positions` must be
re-verified this way — a whole-file-replacement PR cannot catch a regression here.

**On check 5.** A docs-only PR produces zero added code lines. It was still fully reviewed
with a `success` check, confirming M8's distinction: *empty code is not a fetch failure*.
`sentinel_reviews_skipped_total` stayed absent throughout.

## Phase 4b — webhook entry point, without a tunnel ✅

`cloudflared` would have proven three things. All three were instead proven by replaying
realistic GitHub deliveries at `localhost:8000` — signing the exact bytes sent, with real
event names and real payload shapes (nested `repository.full_name`, `pull_request.number`,
`sender.login`).

**14/14 passed:**

| Group | Cases |
|---|---|
| Signature | correct → accepted; tampered body → 401; wrong secret → 401; no header → 401 |
| Event filter | `opened`/`synchronize`/`reopened` → queued; `closed`/`labeled`/`issue_comment`/`push`/`ping` → ignored |
| Dedup | first → queued; same `X-GitHub-Delivery` replayed → `duplicate`; no id → never deduped |

This also proved something the simplified trigger could not: the **real GitHub payload shape**
drives the pipeline correctly. `_extract_owner` / `_extract_repo_name` / `_extract_pr_number`
resolved `notjwp/test-repo#2` from the nested structure, and the review posted.

**What remains unproven:** only the network path — that GitHub's servers can reach a public
URL forwarding to the app. That is DNS/TLS infrastructure, not application behavior, and it
is verified as a side effect of any real deployment.

## Phase 5 — hosting (deferred, not done)

Not provisioned. Every option requires an install or a server, and nothing about the review
pipeline depends on it. Sentinel currently runs via `docker compose` and is triggered on
demand — fully functional.

When it is wanted, the constraint that matters is the **in-process background worker**: it
must not be suspended between requests.

- **Fly.io** runs the existing Dockerfile unchanged with `auto_stop_machines = false` and
  `min_machines_running = 1`. Needs `flyctl`.
- **Oracle Cloud Always Free** ARM VM runs `docker-compose.yml` as-is behind Caddy for TLS.
- **Avoid:** Render's free tier and Cloud Run's default scale-to-zero — both suspend the
  container between requests, dropping queued reviews.

After deploying, point the App's webhook at the host (subscribe to **Pull requests only**) and
re-run Phase 4b against the public URL to close the network-path gap.

## Findings from going live

1. **LLM key was dead.** `403 Forbidden` from NVIDIA on the first real review. The failure-safe
   path worked exactly as designed — the review still posted, with fallback strings — which
   made it invisible except in the log. Key replaced; now `200 OK`.
2. **The LLM prompt sent only rule slugs.** With `1. openai_key\n Severity: HIGH` and nothing
   else, the model reasoned about the *rule name as a variable*: "the variable name
   'openai_key' is not used…" → `openai_key = None`. `LLMService._summarize_finding` now sends
   the description, line, matched code (whitespace-collapsed, capped at `MAX_MATCH_CHARS`),
   and recommendation. Explanations now address the real credential.
3. **The test suite was not hermetic** — see the Phase 2.1 gotcha.
4. **CI had been red since M2**, unrelated to M9: `enrich_findings_with_llm` returns early when
   `ENABLE_LLM` is false, which CI sets, so a test asserting the enrichment marker could never
   pass there. Fixed by pinning the flag in the test.
