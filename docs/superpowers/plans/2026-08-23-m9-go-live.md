# M9 — Go Live: public endpoint, signed webhooks, real-PR validation

## Context

Everything from M1 through M8 — real diff fetch, LLM enrichment, idempotent comment upsert,
Redis durability, semantic corpus, check runs with line-mapped annotations, and M8's event
filter and skipped-review path — has only ever run against fakes and `curl`. 504 tests pass,
but **no GitHub webhook has ever reached this service**, because nothing hosts it: the repo
has `ci.yml` and no deploy path.

Three things block that, and they're ordered by dependency: the app needs a public HTTPS URL,
the endpoint must verify signatures before it's exposed, and only then can a real PR prove the
pipeline end to end.

**Outcome:** a real pull request opens, GitHub delivers a signed `pull_request` event,
Sentinel posts a review comment and a check run with annotations on the correct lines, and a
follow-up comment on that PR is ignored rather than triggering a re-review.

**Decisions taken:**
- **Hosting:** two phases. Phase A validates over a free Cloudflare Tunnel against local
  `docker compose`. Phase B promotes to an always-on host once the pipeline is proven.
  Rationale: nothing about validation requires paid hosting, and debugging is far easier
  against a local container you can `docker logs -f`.
- **Signature verification:** fail-closed **in production only** — a new `ENVIRONMENT`
  setting; when it's `production`, the app refuses to start without `GITHUB_WEBHOOK_SECRET`.
  Local dev and the ~40 existing webhook tests are untouched.
- **Queue:** Redis. Phase A uses the `redis:7-alpine` service already in `docker-compose.yml`;
  Phase B uses a managed instance (Upstash has a free tier).

## Global constraints

- All 504 tests must stay green. The `ENVIRONMENT` default must reproduce today's behavior
  exactly.
- Never commit secrets. `GITHUB_WEBHOOK_SECRET` and `GITHUB_PRIVATE_KEY` go in `.env`
  (git-ignored) or the host's secret store — never in `.env.example`, never in a commit.
- Config only via `get_settings()`.

## Phase 1 — code changes required before exposure

Three changes. Do these first; they're the only code this milestone needs.

### 1.1 `ENVIRONMENT` setting + fail-closed startup check

**`sentinel/config/settings.py`** — add an `ENVIRONMENT: str` field, parsed like the other
string settings, defaulting to `"development"`. Normalize to lowercase.

**`main.py`** — in the lifespan startup, replace the existing warning with a hard failure when
running in production without a secret:

```python
if settings.ENVIRONMENT == "production" and settings.ENABLE_GITHUB:
    if not settings.GITHUB_WEBHOOK_SECRET:
        raise RuntimeError(
            "ENVIRONMENT=production with ENABLE_GITHUB but no GITHUB_WEBHOOK_SECRET — "
            "refusing to start: the webhook would accept unsigned requests."
        )
```

Keep the existing warning for the non-production case. The point is that a misconfigured
production deploy fails loudly at boot instead of silently serving an open endpoint.

**Tests** (`sentinel/tests/test_webhook_signature.py`): production + no secret → startup
raises; production + secret → starts; development + no secret → starts with the warning
(today's behavior, the regression guard for the existing suite).

### 1.2 Protect `/metrics`

`GET /metrics` is unauthenticated and always on — CLAUDE.md already says "firewall it in
public deployments", and this is that moment. It leaks review volume, severity distribution,
and queue depth to anyone who finds the URL.

Simplest correct fix: a `METRICS_TOKEN` setting; when set, `/metrics` requires
`Authorization: Bearer <token>` and returns 401 otherwise. When unset, behavior is unchanged
(so tests and local scraping are unaffected). Implement as a route dependency in
`sentinel/api/metrics_controller.py`, mirroring how `verify_webhook_signature` gates
`/webhook`.

**Tests:** token unset → 200 as today; token set + correct bearer → 200; token set + missing
or wrong bearer → 401.

### 1.3 `$PORT` support in the container (Phase B only, but cheap now)

The Dockerfile hardcodes `--port 8000`. Fly.io and a VPS don't care, but Render, Railway, and
Cloud Run inject `$PORT`. Make the CMD respect it with a default:

```dockerfile
CMD ["sh", "-c", "uvicorn main:app --host 0.0.0.0 --port ${PORT:-8000}"]
```

The `HEALTHCHECK` should use the same variable. Doing this now keeps Phase B a config change
rather than a code change.

## Phase 2 — public endpoint (free, Cloudflare Tunnel)

No hosting bill, no code change, real GitHub deliveries against a container you can watch.

### 2.1 Populate `.env`

Generate a webhook secret and add it — this is the item that has been missing:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Add to `.env` (git-ignored):

```
GITHUB_WEBHOOK_SECRET=<the generated hex>
METRICS_TOKEN=<a second generated hex>
ENVIRONMENT=production
ENABLE_CHECKS=true
LLM_MAX_CALLS=1
```

`ENVIRONMENT=production` here is deliberate: it exercises 1.1's fail-closed path, so a missing
secret is caught now rather than on the real host. Keep `GITHUB_APP_ID`,
`GITHUB_INSTALLATION_ID`, and `GITHUB_PRIVATE_KEY` as they already are.

Note `docker-compose.yml` overrides `REDIS_URL` to `redis://redis:6379/0`, so the compose
Redis is used regardless of the `.env` value.

### 2.2 Start the stack

```bash
docker compose up --build -d
docker compose logs -f sentinel     # keep this open for the whole validation
curl -s localhost:8000/health        # {"status":"ok"}
```

If the container exits immediately, 1.1 is doing its job — check the secret is set.

### 2.3 Open the tunnel

```bash
# One-time: install cloudflared, then
cloudflared tunnel --url http://localhost:8000
```

This prints a `https://<random>.trycloudflare.com` URL. Free, no account needed for the quick
tunnel, and it terminates TLS for you. The URL changes each run — fine for validation; for a
stable URL, create a named tunnel against a Cloudflare-managed domain.

Verify from outside: `curl -s https://<random>.trycloudflare.com/health`.

## Phase 3 — GitHub App configuration

Do this in the App's settings page (Settings → Developer settings → GitHub Apps → your app).

### 3.1 Permissions — **Checks: Read & write is the one that silently fails**

| Permission | Level | Why |
|---|---|---|
| Pull requests | Read & write | comment upsert |
| Issues | Read & write | the comment API is the issues API |
| **Checks** | **Read & write** | **M6 check runs — without it `create_check_run` returns False and only the comment lands** |
| Contents | Read-only | diff, blobs, semantic corpus |

If you change permissions on an already-installed App, **GitHub requires you to approve the
new permissions on the installation** — the App page will show a pending request. Until you
accept it, the token keeps the old scopes and check runs keep failing quietly. This is the
single most likely reason for a "comment appeared but no check run" result.

### 3.2 Webhook

- **Webhook URL:** `https://<random>.trycloudflare.com/webhook`
- **Webhook secret:** the exact value from 2.1
- **SSL verification:** enabled
- **Subscribe to events:** **Pull requests only.** Deliberately not "Issue comments", not
  "Pushes" — M8's filter would ignore them anyway, but not subscribing means GitHub never
  sends them, which is cheaper and makes the delivery log readable.

### 3.3 Confirm the wiring

Save, then check **Advanced → Recent Deliveries**. The `ping` event GitHub sends on save
should show **200** with body `{"status":"ignored","event":"ping"}` — that single response
proves three things at once: the tunnel routes, the signature verified, and M8's event filter
is live.

If it shows **401**, the secret in `.env` and the secret in the App form differ.

## Phase 4 — live end-to-end validation

Use a scratch repo (or a throwaway branch of this one) the App is installed on. Each step
below has an explicit pass condition.

### 4.1 The happy path

Create a branch, add a file with a finding the security engine will certainly catch, and open a PR:

```python
# demo_vuln.py
password = "hunter2"
api_key = "sk-abcdefghijklmnopqrst"
```

**Pass conditions:**

| # | Check | Where | Expected |
|---|---|---|---|
| 1 | Delivery accepted | App → Recent Deliveries | `pull_request` / `opened` → 200 `{"status":"queued"}` |
| 2 | Worker ran | `docker compose logs` | `PR #<n> Risk: HIGH` |
| 3 | Comment posted | the PR | "Sentinel AI Code Review", Risk Score HIGH, both secrets listed |
| 4 | **Check run posted** | PR → Checks tab | "Sentinel AI Code Review", conclusion **failure** |
| 5 | **Annotations on the right lines** | Files changed tab | inline markers on the actual `password` / `api_key` lines, not lines 1–2 |

Step 5 is the one that has never been proven outside a unit test — it exercises the M6
`line_map` built from real patch hunk headers, and it's the most likely thing to be subtly off.

### 4.2 Idempotent upsert (M2)

Push a second commit to the same PR.

**Pass:** the existing comment is **edited in place** — still exactly one Sentinel comment on
the PR. A second comment means `upsert_comment`'s marker lookup is failing. Note a fresh check
run per push is expected and correct (M6 does not upsert check runs).

### 4.3 Event filter (M8) — the new behavior

Post an ordinary human comment on the PR, then close it.

**Pass:** neither produces a new review. If you subscribed only to Pull requests (3.2), the
comment generates no delivery at all; the close generates a delivery answered
`{"status":"ignored","event":"pull_request"}`. Confirm in Recent Deliveries and confirm the
worker log stays quiet.

### 4.4 Docs-only PR (M8 regression)

Open a PR that changes **only** a `.md` file.

**Pass:** a review is still posted, carrying Documentation Issues, with a non-`neutral` check
run. This proves empty added-code is not being treated as a fetch failure — the distinction
M8 was careful about.

### 4.5 Signature enforcement

```bash
curl -si https://<random>.trycloudflare.com/webhook \
  -H 'Content-Type: application/json' \
  -H 'X-GitHub-Event: pull_request' \
  -d '{"action":"opened","repo":"o/r","pr_number":1}'
```

**Pass:** `401`. An unsigned request must be rejected now that a secret is configured.

### 4.6 Metrics protection

```bash
curl -so /dev/null -w '%{http_code}\n' https://<random>.trycloudflare.com/metrics
curl -so /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $METRICS_TOKEN" \
  https://<random>.trycloudflare.com/metrics
```

**Pass:** `401` then `200`.

### 4.7 Durability (M4/M8)

With a review in flight, `docker compose restart sentinel`.

**Pass:** on restart the log shows the job recovered from the processing list and the review
completes. Then confirm the counters look sane:

```
sentinel_webhooks_total{mode="queued"}   / {mode="ignored"}
sentinel_reviews_total{severity="HIGH"}
sentinel_github_posts_total{kind="check_run",outcome="ok"}
sentinel_jobs_processed_total
```

`sentinel_reviews_skipped_total` should be **absent** — if it appears, a PR fetch failed and
M8's skipped-review path fired; check the App's permissions.

## Phase 5 — promote to an always-on host (after validation passes)

Only worth doing once Phase 4 is green. The tunnel dies when your machine sleeps.

**Recommended: Fly.io.** It runs the existing Dockerfile unchanged, and `auto_stop_machines =
false` is the setting that matters — this app's background worker must not be suspended
between requests. Sketch:

```toml
# fly.toml
app = "sentinel-review"
[http_service]
  internal_port = 8000
  force_https = true
  auto_stop_machines = false   # REQUIRED: the worker must stay alive
  min_machines_running = 1
[[http_service.checks]]
  path = "/health"
```

```bash
flyctl launch --no-deploy
flyctl secrets set GITHUB_WEBHOOK_SECRET=... GITHUB_PRIVATE_KEY="$(cat key.pem)" \
                   GITHUB_APP_ID=... GITHUB_INSTALLATION_ID=... \
                   LLM_API_KEY=... METRICS_TOKEN=... ENVIRONMENT=production
flyctl redis create          # sets REDIS_URL for you
flyctl deploy
```

Then update the App's webhook URL to the Fly hostname and re-run 4.1 and 4.3 against it.

**Free alternative:** Oracle Cloud's Always Free ARM VM runs `docker-compose.yml` as-is —
app plus Redis, no code change — behind Caddy for TLS. Genuinely free, but signup and ARM
capacity are the well-known friction.

**Avoid for this app:** Render's free tier and Cloud Run's default scale-to-zero. Both suspend
the container between requests, which is exactly what the background worker cannot tolerate.

*(Verify current pricing yourself — free-tier terms move, and mine may be stale.)*

**Deploy automation** (optional, after the first manual deploy works): add a `deploy` job to
`.github/workflows/ci.yml` gated on `needs: [test, docker]` and `if: github.ref ==
'refs/heads/main'`, running `flyctl deploy --remote-only` with `FLY_API_TOKEN` in repo secrets.

## Verification summary

| Phase | Gate |
|---|---|
| 1 | `pytest` 504+ green, `ruff check sentinel main.py` clean, `docker build` succeeds |
| 2 | `curl https://<tunnel>/health` → `{"status":"ok"}` from outside your network |
| 3 | `ping` delivery → 200 `{"status":"ignored","event":"ping"}` |
| 4 | All of 4.1–4.7 pass, especially 4.1 step 5 (annotation line accuracy) |
| 5 | Same PR flow passes against the permanent hostname |

## Risks and the likely failure modes

1. **Checks permission not re-approved on the installation** — comment lands, check run
   silently doesn't. Symptom: `check run=False` in the log. Most likely single failure.
2. **Annotation lines off by a hunk** — the `line_map` arithmetic has only ever seen synthetic
   patches. Check 4.1 step 5 carefully against a mid-file change, not a new file.
3. **LLM budget** — `LLM_MAX_CALLS=1` means one enrichment call per review and no
   translations. Expected, not a bug.
4. **Tunnel URL rotates** on every `cloudflared` restart; the App's webhook URL must be
   updated each time. Use a named tunnel if this gets annoying.
5. **The sync `code`-in-body path is now internet-reachable** (behind the signature). It was
   meant to be removed in M1. Consider deleting it as part of this milestone — it is the only
   endpoint that analyzes caller-supplied code.

## Out of scope

Tier 2–4 items from the code review (GitHubClient logging and rate-limit handling, the
webhook controller's duplicated branches, the AST security engine) — none of them block
going live.
